## Detailed Problem

Seventeen Indian retailers sell the same transistor. One lists it as `BC547`, another as `BC547 Transistor (Pack of 5)`, a third as `BC547 Transistor – NPN – TO-92 – CDIL`. Each quotes a price per piece, per pack or per reel without saying which, so none of the three prices can be compared to another. Multiply that across 184,801 listings and nobody can tell a buyer what a transistor costs.

Components101, an Indian electronics-components publisher, commissioned Components Radar to answer one question across all of those shops at once: who has this part, and what does it cost? The brief was to get it built and running — to take it from nothing to a working system, then hand it over in a state the client's engineers could carry forward.

Before anything can be compared, the system has to decide which listings are the same thing. That is **entity resolution**: grouping records that describe one real-world object, scattered across sources that never agreed how to describe it. Here it is not a side task but the whole product — without it there is no "this part" to show prices for, only seventeen piles of text. It also punishes carelessness. Merge two different parts into one entry and a shopper sees the wrong price for one of them.

One engineer covered every discipline the product touched: scraping, data modeling, part matching, search, the job runtime that keeps it moving, and the tests. April to August 2026.

**Where it stands.** Collection runs against all 17 retailers, and Components101's public beta is live — a visitor can search for a part and see what the shops are charging. What the beta does not yet do is merge the shops' entries into one row per part, so the same transistor can still appear several times. The matching engine that does that merging was built and delivered, and Components101 is testing it internally before putting it in front of the public. The figures on this page describe the system as handed over; it has continued under a different team since.

### Some stores resist being scraped

Reaching the listings is a problem of its own. The 17 storefronts run on different platforms, and some actively resist automated collection. One bot-protected store supplied well over half of the first run's listings.

## What Was Built

The design is a four-stage pipeline: get the listings in, clean them up, work out which ones are the same part, then make them searchable.

1. **Collect.** Scrape every listing raw and lose nothing early.
2. **Normalize.** Extract part number, manufacturer, category, and specs, and compute a per-unit price so a pack of five compares fairly with a single piece.
3. **Resolve.** Create one canonical record per physical component, keyed on manufacturer part number, so every listing of a part lands on the same entry.
4. **Serve.** Answer searches with hybrid keyword and semantic matching.

### A new store usually slots into an existing scraper

Seventeen stores did not mean seventeen scrapers. Twelve share three reusable paths, and when ten of the 17 were added in a single batch, a probe of each store's homepage, platform-specific API addresses, and telltale HTML patterns sorted eight of the ten onto existing shared scrapers. Only two needed new code.

| Scraper path | Stores | Platforms |
|---|---|---|
| Shopify collection JSON | 6 | Shopify |
| WooCommerce Store API | 3 | WooCommerce |
| Sitemap plus JSON-LD (structured data in each product page) | 3 | No usable API: two WooCommerce, one CS-Cart |
| Bespoke, one path each | 5 | BigCommerce; a Cloudflare-protected store driven through a browser; plain HTML; OpenCart; hand-written PHP |

Every store implements the same two methods, `discover()` to find what to crawl and `process()` to handle each item. Throttling, raw-snapshot saving, error logging, and run accounting come with the shared base, so onboarding a retailer comes down to those two methods and a parser.

### One database instead of three services

Scraping 17 stores means thousands of small jobs, and something has to track which ones are done. That tracker normally arrives as a second piece of infrastructure to run, pay for, and keep in step with the database. Here it lives inside the database itself, so a finished job and the rows it produced are saved in the same breath — a crash cannot leave one without the other, and there is one service to operate rather than three.

It also makes run reports trustworthy. A report is rebuilt from what the database actually holds, and only genuine failures count against a run: a dead link on a store's own sitemap is the store's broken link, not a fault in the collection.

### A false merge costs more than a duplicate

The matching engine keys identity on the manufacturer's own part number, matched exactly. `BC547`, `BC547A`, and `BC547B` are three different gain bins (grades of the same transistor) and stay three records: a false merge puts a wrong price on a real part, while a duplicate row costs only a second glance. Parts that merely do the same job are never grouped (`BC547` and `2N2222` stay apart). Only known clone pairs, such as `SS8050` and `8050` or `LM7805` and `L7805`, are matched, through an alias list that names each pair explicitly rather than inferring it.

When it cannot be certain, it escalates rather than guesses. An exact match on the part number settles most pairs. What is left goes to a similarity check on meaning rather than spelling, and only against listings in the same category from the same manufacturer — comparing every listing against every other would mean roughly seventeen billion comparisons. Anything still unsettled goes to a review queue built for human operators, and only the genuinely ambiguous pairs reach an AI judgment call. A wrong merge never happens silently.

### A cheap prototype settled the search design

Search was the one stage where the right approach was genuinely uncertain, and the wrong answer would have been expensive to unpick later. So rather than build it properly and hope, a deliberately disposable version came first — cheap enough to throw away, real enough to answer the question.

It indexed 132,884 already-classified products from the catalog as it stood at seven stores, matched each query both on wording and on meaning, and used an AI step to read the query's intent before searching. It found the right parts, which was the answer the real build needed.

It worked well enough that Components101 chose to put it in front of users as the public beta rather than wait. That was their call and a reasonable one — but it does mean the live beta is still the prototype, not the production design it was built to validate.

## Course Corrections

Three plans met the actual data and changed. Each correction came from running the system and measuring the result.

### Over a third of listings carry no part number

The plan keyed identity on the manufacturer part number. Measured across the 184,801 listings, 67,128 rows (36.3%) carry no part number at all. Where a part number exists it can still hide several products: `BMP585` resolves to four physically different ones, among them the bare chip and two breakout boards priced at roughly twice and four times as much. Variant suffixes pull the other way: `ESP32-WROOM-32D` and `-32E` are different parts, so a suffix is identity, not noise.

So the rule stayed strict and the merging was deferred rather than forced. Listings with no part number get an identifier assigned by a person, which then behaves exactly like a real one. That converts an unsolvable matching problem into a reviewable one: a queue of known size, worked by people, instead of an algorithm quietly guessing at a third of the catalog.

### One address's reputation was mistaken for three protected stores

Three stores had been written off as reachable only from a home internet connection, never from a rented server. That conclusion rested on tests from a single server address. The first full run put all three on a server host anyway, and all three worked: the original test had measured that one address's bad reputation, not anything about the stores. It cut the other way too — a store with no history of blocking anyone refused the server entirely, and one store turned out to be running a different platform than it appeared to. Which stores go where was inverted, and the original write-up was corrected in place with the evidence that contradicted it, rather than quietly edited.

### A category bonus buried good matches

Category classification first entered search ranking as an additive bonus. The bonus was large relative to the term reflecting where retrieval had placed a result, so one wrong label buried good matches. Two strong matches for a module query, ranked fifth and fourteenth by combined keyword and vector retrieval, fell to 496th and 1,548th once category was applied.

The bonus was replaced with a bounded multiplicative boost: category can lift an already-good match but never push a poorly retrieved one above a well-retrieved one. The bounded form is what the beta runs.

## Outcomes

Components101 ended the engagement with four things: a running collection fleet, a delivered matching engine, a live public beta, and a handover package — a full-codebase review with its fixes, plus a walkthrough written for the engineer taking over.

- **A fleet that runs.** All 17 retailers live end to end; the first full run captured 184,801 raw listings, with 397 tests behind the code.
- **A matching engine, delivered.** Built and handed over; Components101 is testing it internally ahead of its public launch.
- **A live public beta.** Running on the search prototype, comparing prices across retailers, and extended by Components101 since.
- **A handover.** An 1,800-line code walkthrough written for the Go backend engineer Components101 was bringing on: a Python orientation at the front and, at the back, the runtime behaviors that tend to surprise someone arriving from Go.

### Live runs found what the test suite could not

Those 397 tests check logic against sample data, never a real database or a live site — which is fast and reliable, and also means a whole class of problem is invisible to them. A review pass over the full codebase, with every finding checked against live runs on all 17 stores, caught what they structurally could not: among them flaws in how duplicates were checked, how finished runs were closed out, how a malformed queue message was handled, and how pagination decided a store was fully read. All were fixed with regression tests (tests that keep a fixed bug fixed). A green test run would have hidden every one of them.

The review also measured how politely the fleet treats the stores it reads. Four stores had no politeness delay on the product path, and the one that publishes a `Crawl-delay` of five seconds was being fetched a second apart. All four now pause between fetches, and that store honors the full five seconds.

## Limitations

- **The beta still shows one row per shop, not one per part.** The matching engine that fixes this is built and in Components101's internal testing, but until it is switched on a search returns each shop's listing separately. The database already ships with the similarity feature the engine needs, not yet enabled.
- **Two stores can only be read from a home connection.** All 17 run, but those two need that path, which is an operational dependency rather than a solved problem. The fallback that would remove it is built and wired up but has never been switched on, so it is untested.
- **Onboarding a new retailer is cheap; the first one of a new kind is not.** Eight of the last ten stores needed no new code. A storefront on a platform the fleet has not met before still needs its own path written.
